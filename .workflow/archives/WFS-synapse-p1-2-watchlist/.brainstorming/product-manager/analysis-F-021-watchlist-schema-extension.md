# Product Manager Analysis: F-021 WatchlistEntry Schema Extension

## Feature Overview

F-021 extends the existing WatchlistEntry dataclass with two new fields: `priority_score` (float, 0.0-1.0) and `reason` (str, human-readable explanation). This is the foundational schema change that all scoring, ranking, and filtering features depend on.

## User Stories

### US-F021-01: Priority Score Visibility
**As an** investor, **I want** each watchlist entry to display a numerical priority score **so that** I can quickly compare relative importance across stocks.

**Acceptance Criteria**:
- priority_score is present on every WatchlistEntry instance
- priority_score ranges from 0.0 (lowest) to 1.0 (highest)
- priority_score is serialized to both YAML and JSON output formats
- Existing WatchlistEntry consumers without the new fields receive backward-compatible defaults (priority_score=0.0, reason="")

### US-F021-02: Explanation Transparency
**As an** investor, **I want** each watchlist entry to include a reason string **so that** I understand why a stock was included.

**Acceptance Criteria**:
- reason field is present on every WatchlistEntry instance
- reason is a non-empty string when generated by the scoring engine
- reason defaults to "" for backward-compatible legacy entries
- reason string length is between 10 and 200 characters in generated entries

## User Journey Mapping

**Current State (without F-021)**: User receives a flat list of symbols with no scoring or explanation. They must manually assess which items to research.

**Desired State (with F-021)**: Each entry carries a priority_score and reason. The user scans the list top-to-bottom, reads reasons, and makes informed decisions about where to focus.

**Pain Points Addressed**:
- "I don't know which stock on this list is most important" -- solved by priority_score
- "I don't know why this stock is on my list" -- solved by reason field

## Success Metrics

| Metric | Target | Measurement |
|--------|--------|-------------|
| Schema backward compatibility | 100% -- existing code continues to work | Unit tests for to_dict/from_dict round-trip |
| Default value correctness | Legacy entries load with priority_score=0.0, reason="" | Integration test with old YAML files |
| Serialization fidelity | priority_score round-trips within 0.001 tolerance | Round-trip test |

## Priority Assessment

**MoSCoW**: Must

**Rationale**: This is a prerequisite for every other feature in P1-2. Without the schema extension, no scoring data can be stored. The effort is low (adding two fields to a frozen dataclass), and the impact is foundational.

## Dependencies

- **Upstream**: Existing WatchlistEntry definition in `synapse/schemas/watchlist.py`
- **Downstream**: F-022 (scoring engine writes to priority_score and reason), F-026 (ranking reads priority_score), F-028 (tests validate schema)
- **Cross-role**: data-architect defines the schema; product-manager defines the user-facing contract (range, semantics, reason format)

## Constraints & Risks

| Constraint | Type | Mitigation |
|------------|------|------------|
| Backward compatibility | MUST | Lazy Upcast: new fields get default values on load |
| Frozen dataclass immutability | MUST | New fields added at construction time; no mutation after creation |
| SignalType enum independence | MUST NOT | WatchlistEntry.SignalType MUST NOT be merged with schemas/signal.py.SignalType |
| YAML/JSON round-trip fidelity | MUST | to_dict/from_dict MUST produce identical output for new fields |

## Product Considerations

The priority_score range (0.0-1.0) is a user-facing contract. Users will mentally map scores: 0.8+ means "high priority", 0.5 means "moderate", below 0.3 means "low but worth watching." The schema extension SHOULD enforce this range at the data level (validation in __post_init__ or factory method) to prevent out-of-range values from reaching users.

The reason field is the trust-building mechanism. A watchlist entry without a reason is a black box. The product requirement is that ANY entry generated by the scoring engine MUST include a reason string that references at least one contributing signal.
